# 我的菜谱：自己加菜，联网自动补全

版本 0.2.0（versionCode 9）。入口在「我的 › 我的菜谱」，也可以在「我的」页的卡片里直接点「添加菜谱」。

## 一次添加是什么样的

1. 输入菜名，回车或点「联网补全资料」。
2. **有网络**：按菜名去 HowToCook（`Anduin2017/HowToCook`，Unlicense）匹配，抓到页面后把简介、材料与用量、步骤、观察提示、注意事项、用时、难度、菜式分类一起填进表单，顶部提示「已按〈某道菜〉补全资料」。
3. **没网络 / 库里没有 / 请求失败**：表单照常可填，只多一行说明。**任何情况下都不会因为联网失败而挡住手动录入。**
4. 用户改完点「保存」。从菜名到步骤、从封面到份量，每个字段都能改，预填只是起点。

编辑已有菜谱走同一个表单，id 不变，所以收藏与浏览记录不会断。

## 联网补全的实现

- **索引随包发**：`app/src/main/assets/howtocook_index.json` 里有 372 个菜名到页面路径的映射，外加一个**固定的 commit**（当前 `743d7f4`）。所以菜名匹配是离线的、瞬时的，联网只为取那一页正文；同一道菜永远取到这个项目审过的版本。
- **每次查找只发一个请求**：`https://raw.githubusercontent.com/Anduin2017/HowToCook/<commit>/<path>`。不需要 API Key、不需要账号、不经过任何第三方服务。
- **没有后端**：App 只读公开仓库的文本，不上传任何东西。
- **名称匹配分三级**（`DishMatcher`）：完全相同 → 互相包含（取长度最接近的那个）→ 字符二元组重合度 ≥ 0.55。第三级带常见同义词归一（西红柿↔番茄、土豆↔马铃薯、包菜↔卷心菜等）。
  阈值是刻意收紧的：`韭黄炒鸡蛋` 不会去借 `西红柿炒鸡蛋` 的资料（实测重合度 0.50），而 `番茄炒蛋` 能匹配到 `西红柿炒鸡蛋`（0.57）。
- **解析**（`HowToCookParser`）：按 `## 必备原料和工具` / `## 计算` / `## 操作` / `## 附加内容` 分段。`计算` 段上游有两种写法（`西红柿 = 1 个 * 份数` 和 `肉蟹 1 只（大约 300g） * 份数`），两种都读；材料名允许别名（`青蟹（别称：肉蟹）` 能对上 `肉蟹` 的用量）。
- **宁可空着也不编**：抓不到就留空，不猜测、不生成。页面里没有的字段（比如用时）保持空值，界面显示「—」。

## 匹配错了怎么办

直接改。预填只是填空，不锁定任何字段；提示里写明了按哪道菜补的全、来自哪个库。再点一次「联网补全资料」时，**已经填过的字段不会被覆盖**，只补还空着的部分——所以第二次搜索不会冲掉用户已经改过的手写内容。

## 数据放在哪

| 内容 | 位置 | 说明 |
| --- | --- | --- |
| 用户菜谱 | DataStore `user_recipes.json` | 与 `user_data.json`（收藏/偏好）分开存，互不牵连 |
| 封面 | `filesDir/covers/cover-<uuid>.jpg` | 4:3、1200×900、JPEG q82，与内置配图同规格 |
| 菜谱 id | `user-` 前缀 | 区分「我的」和内置内容，不需要额外字段，也不会与内置 id 撞号 |

- 内置内容仍然只在 `assets/recipes.json`，不会被用户操作改写。
- 用户菜谱文件损坏时按既有约定报错并**保留原文件**，内置 112 道照常可用。
- 删除一道菜谱时同时删掉它的封面文件，并从收藏和浏览记录里摘掉这一条。

## 和内置菜谱的关系

用户菜谱并入同一个列表（内置在前、自建在后），所以：

- 首页、搜索、收藏都能搜到、能收藏；
- 卡片右上角有「我的」标记，列表行标题旁也有；
- 详情页、分步阅读、评分筛选、用时筛选全部复用既有实现，没有第二套展示逻辑。

用户菜谱永远不会进入「精选」（`featured` 恒为 false）。

## 与内容模型的一致性

保存前按内置内容的同一套规则校验（`RecipeDraft.problems()`）：菜名非空、地域必须取 7 个白名单值、分类至少一个且取自 11 个菜式、用时 1–1440、难度 1–5、份量非空、材料与步骤各至少一条。步骤 id 自动生成为 `<recipeId>-sN`，材料 id 为 `i0..in`，空行自动丢弃。

所以「我的菜谱」产出的数据结构和内置内容完全一致，校验脚本、单元测试、筛选逻辑都不需要特例。

## 权限与隐私

新增两项权限，都只为这一步服务：

- `INTERNET`：取那一页菜谱正文。
- `ACCESS_NETWORK_STATE`：判断当前有没有网，避免无网时干等超时。

除此之外不采集、不上传、不写入任何账号或设备信息；不联网时全部功能（112 道内置菜谱、收藏、我的菜谱的增删改查）都照常可用。

## 工具

- `tools/build_howtocook_index.py`：重新生成菜名索引（默认钉在 master 的最新 commit，也可 `--ref <sha>` 指定）。内容需要刷新时才跑，跑完看 diff 再提交。
- `tools/validate_content.py`：新增索引检查——来源与许可、commit 必须是 40 位 sha、路径必须以 `dishes/` 开头且与菜名一致、菜名不重复、条目数不能少得可疑。

## 测试

- `HowToCookParserTest`（7 项）：标题、简介、难度、用时、材料与用量合并、子条目转观察提示、注意事项、无可用步骤时返回 null。
- `DishMatcherTest`（7 项）：完全匹配、忽略空格标点、同义词归一、包含匹配取最具体、近似名匹配、拒绝只是长得像的菜。
- `RecipeDraftTest`（10 项）：缺项提示、越界值、空行丢弃、id 生成、「无」占位、来源标注、不完整草稿拒绝成菜、编辑回填。
- `UserRecipeStoreTest`（5 项）：同 id 原地替换、删除、序列化往返、损坏文件与非法内容均报错而不覆盖。

解析器另外用**全部 372 页真实页面**（钉在同一个 commit）做过一次离线核对，结果是：372 页全部解析成功、0 失败；材料行里 77%（2441/3160）读到了用量，341 个页面的材料至少有一项用量；步数 2–38，平均 9。另外 31 页（多为饮品和烘焙）上游本身没写用量，就留空。这一步是人工核对的，不联网的测试不进仓库。

## 已知限制

1. 只覆盖 HowToCook 里的 372 道菜；库里没有的菜只能手填（这是选定单一数据源的结果）。
2. 上游正文是"程序员菜谱"风格，用词与家常说法不完全一致；预填后要按自己的做法改。
3. 自动补全填的内容**没有试做验证**，来源页上写明了，界面提示里也写了。
4. 中文与西式都有，但地域一律按「中式」预填（上游不标地域），需要的话自己改。
5. 封面来自相册，会复制进应用目录；卸载应用时一起删除，不做云备份。
